1. Мета роботи

Навчитись використовувати JMeter для тестування продуктивності REST API, налаштувати кореляцію динамічних даних, зібрати та проаналізувати метрики продуктивності й ресурсів системи, а також запропонувати стратегії оптимізації.

2. Налаштування середовища

  • Запущено Docker-контейнер з тестованим додатком: 
    docker run -p 3001:3001 oleksandrgolubishko/qa_pro_rest_app
  • Додаток підтверджено доступним за адресою http://localhost:3001.
  • Тестовий інструмент: Apache JMeter 5.6.3, запуск виключно в CLI-режимі (-n, non-GUI) — офіційно рекомендований спосіб запуску реальних тестів, оскільки GUI-режим призначений тільки для розробки та налагодження тест-плану і споживає зайві ресурси на відмальовування графіки в реальному часі.

3. Структура тест-плану

Тест-план (test1(performance).jmx) містить повний CRUD-цикл роботи з сутністю "character":

№ЗапитМетодОпис
1GET all charactersGETОтримати список усіх персонажів
2POST create characterPOSTСтворити нового персонажа
3GET character by idGETОтримати створеного персонажа за ID
4PUT update characterPUTОновити дані персонажа
5DELETE characterDELETEВидалити персонажа

Додаткові елементи:

  • HTTP Header Manager — задає загальні заголовки для всіх запитів.
  • Constant Timer (1000 мс) — штучна пауза між ітераціями, додана для того, щоб тест тривав достатньо довго для коректного моніторингу ресурсів (див. розділ 5).
  • Thread Group: 1 користувач (Number of Threads = 1), 30 повторів (Loop Count = 30) — послідовне навантаження без паралелізму, щоб чітко бачити поведінку кожного окремого циклу запитів.

4. Кореляція та динамічні дані

Оскільки id персонажа генерується сервером динамічно під час виконання POST create character, для коректної роботи наступних запитів (GET by id, PUT, DELETE) використано техніку кореляції:

  • Додано JSON Extractor на запит POST create character:
    • Variable name: characterId
    • JSON Path: $.id
    • Default Value: NOT_FOUND (для діагностики у разі помилки вилучення)
  • URL-адреси наступних запитів оновлено на ${baseUrl}/character/${characterId}.

Перевірка кореляції: проведено окремий CLI-прогін з аналізом .jtl-файлу результатів. У логах підтверджено, що всі запити (GET by id, PUT, DELETE) використовували один і той самий реальний ID (наприклад, character/4), отриманий з відповіді POST, а не значення NOT_FOUND. Усі відповіді мали статус 200 OK / 201 Created, що підтверджує коректність ланцюжка запитів.

5. Listeners та моніторинг ресурсів

5.1 Listeners для метрик продуктивності

У тест-плані використано:

  • View Results Tree — перегляд деталей кожного окремого запиту/відповіді.
  • Aggregate Report — зведена статистика (середній/мінімальний/максимальний час відповіді, перцентилі, throughput, % помилок).
  • Graph Results — візуальний графік часу відповіді, throughput та відхилення в реальному часі.

5.2 Моніторинг ресурсів (CPU/RAM)

Спочатку планувалось використати плагін PerfMon (jp@gc - PerfMon Metrics Collector) через ServerAgent. Плагін було успішно встановлено через JMeter Plugins Manager, ServerAgent запускався і навіть встановлював TCP-з'єднання з JMeter (Accepting new TCP connection, Starting measures: memory: cpu:), проте аварійно завершувався (EXCEPTION_ACCESS_VIOLATION) через конфлікт застарілої бібліотеки sigar (2017 р.) з сучасною версією Java Runtime Environment, встановленою в системі.

Прийняте рішення: оскільки завдання прямо допускає використання "PerfMon або іншого відповідного Listener", моніторинг ресурсів здійснено через вбудований Диспетчер завдань Windows (вкладка "Продуктивність" → CPU / Пам'ять), синхронно зі запуском навантажувального тесту через CLI.

Результати спостереження під час прогону (30 циклів × 5 запитів, ~2,5 хв):

ПоказникДо тесту (baseline)Під час тесту
CPU~6%5–10%, з періодичними сплесками до ~10-11%, що відповідають моментам обробки запитів Docker-контейнером
RAM10,7 / 15,4 ГБ (69%)11,0–11,3 / 15,4 ГБ (71–73%)

Зафіксовано серію скріншотів графіків CPU та Memory до, під час і після прогону тесту — додано до git-гілки як докази моніторингу. Результати цього прогону збережено у файлі performamce_monitoring.jtl.

Виявлене вузьке місце

Запит GET all characters демонструє суттєвий викид: максимальний час відповіді (25 мс) і 99-й перцентиль (25 мс) значно перевищують показники решти запитів (3–5 мс), тоді як медіана (2 мс) залишається низькою. Це вказує на одноразову аномалію в одному з 30 виконань, а не на системну проблему.

Ймовірна причина: запит повертає повний список персонажів, розмір якого динамічно змінювався протягом тесту (кожен цикл додавав і видаляв по одному персонажу). Найімовірніше, пік стався в момент, коли база даних або мережеве з'єднання ще не було "прогріте" (перший виклик у циклі), або в момент паралельної операції запису.

Показники стабільності

  • Error rate: 0.00% по всіх типах запитів — сервер жодного разу не повернув помилку.
  • Кореляція (characterId) відпрацювала коректно у всіх 30 ітераціях без винятків.

6.1 Стрес-тестування з паралельними потоками

Додатково до основного сценарію (1 послідовний користувач) проведено стрес-тест з конкурентним навантаженням (окремий тест-план test2(stress).jmx — копія основного плану зі зміненими параметрами Thread Group):

  • Number of Threads (users): 20 (паралельні віртуальні користувачі)
  • Ramp-up period: 5 секунд
  • Loop Count: 5 (кожен користувач)
  • Constant Timer: 0 мс (без штучних пауз — максимальне навантаження)
  • Загальна кількість запитів: 20 × 5 × 5 = 500
СценарійUsersЗапитівТривалістьThroughputMax час відповідіErrors
Послідовний (baseline)11502 хв 31 сек1.0/сек25 мс0.00%
Стрес-тест (паралельний)205005 сек104.2/сек24 мс0.00%

Висновок стрес-тесту: навіть під навантаженням у 104 запити/секунду (майже у 100 разів вище за базовий сценарій), додаток утримав 0% помилок, а максимальний час відповіді (24 мс) залишився на тому ж рівні, що й при значно меншому навантаженні. Це свідчить про хорошу здатність REST API обробляти конкурентні запити без деградації стабільності в межах протестованого діапазону навантаження.

Під час стрес-тесту зафіксовано моніторинг ресурсів через Диспетчер завдань: спостерігались більш виражені та часті піки CPU (порівняно з послідовним сценарієм), що логічно відповідає значно вищій інтенсивності запитів за одиницю часу. Результати цього прогону збережено у файлі stress_minitoring.jtl.

7. Стратегії оптимізації

  1. Пагінація для GET all characters — повертати список частинами (наприклад, по 20-50 записів), а не повністю, щоб уникнути зростання часу відповіді при збільшенні кількості даних.
  2. Індексація бази даних — додати індекси для пришвидшення операцій вибірки, особливо для GET all.
  3. Кешування — якщо список персонажів не змінюється надто часто, розглянути кешування відповіді GET all characters на короткий проміжок часу.
  4. Розширене навантажувальне тестування — провести додаткові прогони з більшою кількістю паралельних потоків (Number of Threads > 1) та без штучних пауз (Constant Timer), щоб перевірити, чи виявлений пік у 25 мс є систематичною проблемою під реальним конкурентним навантаженням, чи одноразовою аномалією.
  5. Стрес-тестування — поступово збільшувати кількість користувачів (наприклад, 10 → 50 → 100) для визначення точки, після якої час відповіді або error rate починають суттєво зростати.

8. Висновки

REST API тестованого додатку демонструє високу стабільність (0% помилок) і низький середній час відповіді (2-3 мс) під поточним рівнем навантаження. Технічна кореляція динамічних ID реалізована та підтверджена коректно. Виявлено одне потенційне вузьке місце в запиті отримання повного списку сутностей, для якого запропоновано конкретні шляхи оптимізації. Моніторинг ресурсів системи (CPU/RAM) показав помірне навантаження без ознак виснаження ресурсів під час тесту.
